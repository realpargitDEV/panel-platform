# Remote Management

One desktop client manages agents on other machines. The intended arrangement:
an old Linux box in a cupboard runs the agent and hosts the projects; the
Windows desktop runs the client and manages it.

**This is not screen sharing.** No framebuffer, no input forwarding, no
AnyDesk. The client speaks the same typed API it uses locally, to a different
address. That is the entire difference — which is why remote support costs
almost no extra surface area.

---

## 1. Default posture

The agent binds `127.0.0.1:8787`. In that state no other machine can reach it at
all, regardless of firewall configuration. LAN access requires two deliberate
acts:

1. Enabling LAN binding in settings — audited, and refused while data-directory
   permissions are wrong.
2. Consenting to a firewall rule, scoped to the detected local subnet and to
   private network profiles only.

The agent is never exposed to the public internet by design. Crossing networks
is Tailscale's job (§5).

---

## 2. Pairing

A remote client must prove it was authorised by someone with access to the host.
A password alone would not do that — passwords are phishable and replayable, and
the host may be headless.

```
Host                                     Remote client
────                                     ─────────────
1. Generate pairing code
   • 8 chars, Crockford base32
   • valid 10 minutes, single use
   • only the Argon2id hash stored
   • shown in the UI or by
     `project-host-ctl pair --new`
                              ──────▶  user types the code

2.                                      Generate Ed25519 device keypair
                                        • private key → OS keychain
                                        • never leaves the machine
                              ◀──────  POST /clients/pair
                                        { code, public_key, label, platform }

3. Verify code, store TrustedClient
   • public key, fingerprint, label
   • mark code consumed
   • audit entry
                              ──────▶  { cert_fingerprint, client_id }

4.                                      Pin cert_fingerprint
                                        Store connection record
```

Nothing secret crosses the wire in step 2 or 3: the client sends a public key,
the agent returns a certificate fingerprint. Interception yields nothing usable,
and the pairing code is consumed on first use, so a captured code cannot be
replayed.

---

## 3. Authenticating afterwards

Every session starts with a challenge. Possession of the device key is what
authenticates, so there is no long-lived shared secret to steal.

```
client → POST /auth/challenge  { client_id }
agent  → { nonce, expires_at }              nonce: 32 bytes, single use, 60s
client → POST /auth/verify     { client_id, signature }
agent  → verify Ed25519 against stored public key → session token
```

Nonces are single-use and time-bounded, which closes replay. The resulting
session behaves exactly like a local one: absolute and idle expiry, revocable,
bound to the client.

Revoking a client deletes its public key and kills its sessions in the same
transaction. A revoked laptop loses access on its next request, not at the next
expiry.

---

## 4. Transport security

- TLS 1.3 only, self-signed certificate generated by the agent at first start.
- The client pins the **SPKI SHA-256 fingerprint**. No CA, no system trust store,
  no expiry cliff.
- A changed fingerprint is a **hard stop**. The UI shows the stored and presented
  fingerprints side by side and requires explicit confirmation. It is never a
  click-through, because this is the single signal distinguishing a reinstalled
  agent from an interception attempt, and habituating the user to accepting it
  would spend that signal for nothing.
- Fingerprints are displayed grouped in short blocks so a human can actually
  compare them against what the host shows.

## 5. Addressing

| Kind        | Example                           | Notes                                      |
| ----------- | --------------------------------- | ------------------------------------------ |
| `LOCAL`     | `127.0.0.1:8787`                  | Same machine                               |
| `LAN`       | `192.168.1.40:8787`               | Requires LAN binding                       |
| `TAILSCALE` | `100.x.y.z:8787` or MagicDNS name | Recommended for crossing networks          |
| `MANUAL`    | any host:port                     | For VPNs and tunnels the user already runs |

Tailscale is the recommended answer to "manage it from outside the house"
because it moves authentication, encryption and NAT traversal to a system built
for exactly that, instead of inventing a hole-punching scheme here. Project Host
does not bundle, install or require it; it simply works over the interface if
one exists. If a Tailscale interface is detected, the UI offers the address.

mDNS discovery of agents on the local network is a listed future feature, not a
version-one one. Broadcasting the presence of a management API is a decision
that deserves its own design.

## 6. Connection lifecycle

```
DISCONNECTED → CONNECTING → AUTHENTICATING → CONNECTED
                    ▲                            │
                    └──── RECONNECTING ◀─────────┘
                              │
                              └──▶ FAILED (auth rejected, pin mismatch)
```

- Heartbeat every 20s; two missed beats close the connection.
- Backoff 1s → 30s with jitter; unlimited retries while the user keeps the
  connection selected.
- On reconnect, the client resubscribes to its topics and refetches current
  state rather than trusting its cache.
- `FAILED` states — revoked client, pin mismatch — do not retry. They need a
  human, and retrying would only obscure that.

**Disconnection changes nothing on the host.** Projects keep running, logs keep
being written, backups on a schedule keep happening. The client is an observer,
and losing an observer is not an event the system reacts to.

---

## 7. Multiple servers, multiple clients

The client's sidebar lists connections; switching is instantaneous and each
connection keeps its own session, stream and cache. Two agents can be watched at
once — one connection is active in the main view, others hold their subscriptions
if they have live operations.

An agent accepts several paired clients. Each has its own device key, sessions
and audit trail, so "who restarted the bot" is answerable per device. The
`/clients` screen lists them with last-seen times and one-click revocation.

---

## 8. What is not built

Stated so the boundary is unambiguous:

- No screen sharing, remote desktop, or input forwarding.
- No relay or rendezvous server — every connection is direct.
- No cloud account, and no public exposure by default.
- No agent-to-agent communication; agents do not know about each other.
- No file transfer between two agents; export and import go through the client.
